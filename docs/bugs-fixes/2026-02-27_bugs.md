## BUG-11: Weight/reps input too slow with +/- stepper buttons
**Status:** FIXED (2026-02-27)
**Priority:** P1 (high)
**Reported:** 2026-02-27
**Screen:** Active Workout (`WorkoutScreen.kt`)

### Problem
The `[ - 20 + ]` stepper requires too many button presses to change weight significantly. Mid-workout data entry is frustratingly slow.

### Root Cause
Design decision — stepper was the original input method. Not suitable for real-world gym use.

### Fix
Two new input methods:
1. **Single tap** → opens simplified bottom sheet with large numeric text field + keyboard (replaced +/- stepper). Auto-selects text for immediate typing. Snaps weight to 0.5kg increments.
2. **Long-press + drag up/down** → continuous value adjustment directly on the set row. 2.5kg per ~30dp for weight, 1 rep per ~30dp for reps. Haptic feedback on each step.

Existing `NumberInput` component preserved for PlanReview screen. Changes isolated to `NumberInputSheet` (simplified) and `SetRow` ValueCell (new drag gesture). Drag callbacks default to null — SessionDetail and PlanReview screens unaffected.

### Files
- `core/ui/component/NumberInputSheet.kt`
- `core/ui/component/SetRow.kt`
- `feature/workout/active/components/ExerciseCard.kt`
- `feature/workout/active/WorkoutScreen.kt`

## BUG-12: Drag-to-adjust weight/reps only changes one step, then erratic
**Status:** FIXED (2026-02-27)
**Priority:** P1 (high)
**Reported:** 2026-02-27
**Screen:** Active Workout (`SetRow.kt`)

### Problem
Long-press-drag gesture on weight/reps only shifts one value, then behaves erratically (jumps between values). Cannot drag from 20 to 60 as intended.

### Root Cause
Stale closure: `onDragStepChange` lambda captured `displayWeight` at compose time. `pointerInput(Unit)` never restarts, so the lambda references the original value after state updates. Multiple steps in one frame all computed from the same stale base.

### Fix
- Replaced `onDragStepChange` with `currentNumericValue`, `dragStepSize`, `dragMinValue`, `dragMaxValue`, `onDragValueChange` params on ValueCell
- Used `rememberUpdatedState` for callback and value inside ValueCell
- Cumulative displacement model: on drag start, captures `startValue`; during drag, computes `totalSteps = accumulatedPx / threshold`, then `newValue = startValue + totalSteps * stepSize`
- Each new drag gesture starts from the latest value — no stale closures

### Files
- `core/ui/component/SetRow.kt`

## BUG-13: Template does not remember exercise order
**Status:** FIXED (2026-02-27)
**Priority:** P2 (medium)
**Reported:** 2026-02-27
**Screen:** Create Template (`CreateTemplateViewModel.kt`)

### Problem
Saving a workout as a template loses the user's exercise order. Loading the template shows exercises in arbitrary (Room PK) order.

### Root Cause
`CreateTemplateViewModel.loadExercisesFromIds()` calls `exerciseRepository.getExercisesByIds(ids)` which uses `WHERE id IN (:ids)`. Room's `IN` clause returns rows in SQLite's own order (typically PK), not the input list order. The subsequent `mapIndexed` assigned `orderIndex` based on the scrambled order.

### Fix
- Re-ordered fetched exercises using `associateBy { it.id }` + `ids.mapIndexedNotNull` to match original input order
- Same pattern already used in `handleLoadTemplate` and `loadExistingTemplate`
- Added unit test verifying order preservation when Room returns different order

### Files
- `feature/templates/CreateTemplateViewModel.kt`
- `feature/templates/CreateTemplateViewModelTest.kt` (new test)

## BUG-14: Multi-muscle-group exercise ordering not interleaved
**Status:** FIXED (2026-02-27)
**Priority:** P2 (medium)
**Reported:** 2026-02-27
**Screen:** Exercise Order (`OrderExercisesUseCase.kt`)

### Problem
When selecting exercises from multiple muscle groups (e.g., 3 chest + 3 back), default order groups all of one muscle together (chest-chest-chest-back-back-back) instead of interleaving.

### Root Cause
`OrderExercisesUseCase` concatenated compounds + isolations + core without considering muscle group distribution.

### Fix
- Replaced concatenation with round-robin interleaving across muscle groups
- Groups sorted by size descending (largest leads each round)
- Within each group: compounds before isolations, then by orderPriority
- Core exercises always last (unchanged)
- Added 5 unit tests covering equal groups, unequal groups, 3+ groups, within-group sort, and core-last invariant

### Files
- `core/domain/usecase/OrderExercisesUseCase.kt`
- `core/domain/usecase/OrderExercisesUseCaseTest.kt` (5 new tests)
